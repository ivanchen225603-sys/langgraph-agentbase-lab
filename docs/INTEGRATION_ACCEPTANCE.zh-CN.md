## 真实浏览器验收

通过浏览器直接操作产品页面，没有注入测试脚本：

1. 创建慢旧任务、点击取消，页面显示“正在收尾，任务尚未结束”。
2. 在收尾期间提交新需求，新 Run 立即被接纳；单 worker 场景下，实际执行仍等待旧任务释放槽位。
3. 释放合成清理门后，旧处理器故意生成晚到候选；新任务完成，当前结果只含 `NEW_RESULT_MARKER`，旧候选未发布。
4. 自动观察将旧任务更新为“清理已完成”，没有手动查询终态。取消 POST 只发生 1 次。
5. 独立注入存储收尾失败，页面显示“收尾状态未知，尚未确认任务已结束”，没有误报完成。

本轮保存 5 张截图、DOM、事件和最终状态；两个 loopback 验收服务已正常退出。这是两个浏览器场景，不并入 pytest 数量。

本地详细记录为 `evidence/integration-v1/pytest.xml`、`coverage-packages.json`、`tracked-export.xml`、`artifact-browser-audit.json`、`installed-wheel.json`、`protection-final.json` 和 `verification.json`。这些证据未纳入 Git，可从执行本轮验收的工作目录查看。

## 下一步最小方案：提案、确认、执行分离

仅提出以下一条接入流程，本轮不实施新 API/UI：

1. 已认证宿主创建请求 ID，绑定会话 epoch、目标 Run、需求版本及规范化输入摘要；调用现有 IntentDecision，只返回解释、澄清或提案。模型不提供身份、scope 或批准状态。
2. UI 展示原需求、目标与确切新输入；用户单独确认该版本。宿主保存有期限、可单次消费的确认记录，晚到提案或旧版本不能替代当前确认。
3. 执行层在实际准入/控制事务中再次校验身份、Agent ACL、scope、目标 Run、需求版本和 epoch，再调用既有 RunEngine。写工具仍需自身的精确审批；新任务不继承旧计划或旧审批。换题操作必须明确其会话级影响。

这一接入还需独立验证，未验证前不把意图自动映射为副作用。取消不等于回滚，未知写结果仍需可信回执核对。
